## R85 — Frontend canonical-route DB failure truth

**Review completed before correction.** Canonical rewrite/query-var routing, `route_visible()`, repository failure signaling, direct channel lookup, route-template status selection and the existing shortcode-only frontend DB guard were reviewed together.

**Frozen finding:** deep-link visibility checks could convert a database outage into a false 404. Video/live lookups used the repository but `route_template()` ignored `VWLB_Repository::read_failed()`; the channel lookup used direct `$wpdb` without testing `last_error`. R60's frontend DB guard only wraps selected shortcode output and therefore could not correct the HTTP status chosen earlier by `template_include`. This violated the plan's distinct degraded/error-state requirement and could misrepresent service failure as nonexistence.

**Correction:** route visibility now returns a dedicated 503 error on repository/direct-DB read failure; `route_template()` distinguishes that from a genuine not-found state, emits no-cache 503 and records an operational failure; `templates/route.php` renders an explicit temporary-unavailability state instead of executing route shortcodes when the route truth cannot be verified.

**Regression gate:** R85 static contracts assert repository failure detection, direct DB error inspection, HTTP 503 and the unavailable template state.

**Retest:** exact-head File 10 Release QA run `33293990479` completed successfully before R86.

## R86 — Privacy-erasure uniqueness and multi-user retention audit

**Review completed before correction.** Privacy erase batching was compared with the schema constraints for retained live-attendee consent and creator aggregate records.

**Frozen finding:** retained rows were anonymized by setting `live_attendees.user_id` and `creator_metrics_daily.owner_id` to literal `0`. Both columns participate in unique keys (`event_user` and `metric_object`). After one user's retained row had been anonymized to zero, erasing a second user with a row for the same live event or the same metric date/object could violate the unique key, roll back the erasure transaction and make legitimate multi-user privacy requests fail deterministically.

**Correction:** each erasure batch now generates a high-range one-way/randomized anonymized subject surrogate. Unique-constrained retained identity columns use that surrogate instead of zero, preserving record uniqueness while severing the original WordPress user identifier. Non-unique retained attribution fields continue to use zero where appropriate.

**Regression gate:** R86 contracts assert the surrogate helper, its use on both unique-constrained retained tables, absence of the old zero assignments and continued presence of the governing unique-key schema contracts.

**Retest:** exact-head File 10 Release QA run `33294175427` completed successfully before R87.
